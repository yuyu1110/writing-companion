# 从需求到写作伴侣

本文整理项目的设计演进，解释哪些问题促成了今天的结构。它不是逐字聊天记录，也不是已经完成所有未来功能的宣告。

## 1. 先确定作者和助手的分工

起点有四个目标：吸收文学与写作指导资料、整理已完成作品、接续未完成作品、逐步提高写作能力。随后明确以散文随笔为主、小说为辅；助手应多提问、反馈、质疑与共同构思，必要时示范。

由此把“立即给一篇更漂亮的稿子”改成可讨论的协作：判断要指向具体文字，解释效果与选择，保留作者执笔和采纳的权利。明确要求改写时仍可以生成候选，避免把作者困在无休止的问答里。

## 2. 把对话习惯变成可调用的规则

为新对话复用协作方式，建立一个 Skill 入口，再将编辑、教学、风格、检索、资料维护和工作区记录拆成按需阅读的参考文件。长期偏好和会话进度放入工作区，不把每次聊天的临时判断写成全局命令。

早期参考了以下公开项目的设计思路。链接是当时研究记录中的来源，文件位置或内容可能随后变化；本项目按中文写作需求重述规则，未打包这些项目的源文件。

| 参考项目 | 启发与本项目的取舍 |
|---|---|
| [haowjy/creative-writing-skills](https://github.com/haowjy/creative-writing-skills) | 构思、分层审稿、读者体验和风格分析；保留作者意图，模拟阅读反应不冒充独立读者实测 |
| [anthropics/skills · doc-coauthoring](https://github.com/anthropics/skills/tree/main/skills/doc-coauthoring) | 局部迭代与读者可理解性；不照搬固定批量问卷 |
| [aws-samples/sample-knowledge-acquisition-skill](https://github.com/aws-samples/sample-knowledge-acquisition-skill) | 原始资料、知识整理与关联分离；文学观点可以并存，不按新旧淘汰 |
| [ktaletsk/learn-codebase](https://github.com/ktaletsk/learn-codebase) | 逐步提示与独立运用检查；文学选择不设唯一正确答案 |

通用包装结构遵循 [OpenAI Skill 文档](https://learn.chatgpt.com/docs/build-skills) 的入口与支持文件方式。参考不等于依赖，也不意味着这些项目为本 Skill 背书。

## 3. 让书库成为能核对的材料

正文统一转换为 Markdown，同时保留来源、作者、版本、译者、获取范围与提取缺陷。实际整理中遇到过合集标称册数与目录不一致、目录跳转异常、同名或近名作品混淆等情况，因此不能凭文件名宣称“完整版已读懂”。

资料准入由最初的严格完整版本要求，调整为可以使用不同版本与部分文本，但必须标明覆盖范围。这个变化影响的是可用材料的范围，不降低引用核验要求。公开模板采用这一默认规则，使用者可以调整。

## 4. 从找关键词走向有依据的对读

早期目录与精确字符串搜索便于查已知文字；之后增加 SQLite FTS5、中文双字词元、概念线索组、候选去重与输出预算。查询先发现候选，再读取原文与前后文，避免把命中的孤立句当作解释。

阅读卡保存实际读过的范围、分析与证据哈希，用于以后复用。开放范例发现仍覆盖整个适用书库，不能只围绕新导入或刚讨论的作品。现阶段没有实现向量语义搜索，也没有把书库训练进模型。

## 5. 把“要有理有据”落实到反馈

反馈逐步明确为三类不同材料：文学原文展示处理方式，指导书观点提供可讨论的方法，原创短示范帮助尝试。引用必须回到原文，人物台词不能直接当成作者主张，二手转引不能冒充一手核验。

修改建议也需要保留反例和适用条件：抽象表达、重复、对称和含混都可能有效，不能凭一条写作口诀统一删改。对于纪实写作，示范中的虚构细节必须明确标注。

## 6. 整理文档并准备发布

后续整理缩短入口，将重复的引用、保存与教学说明归并到各自负责的文档。发布包进一步加入空白工作区、安装说明、格式文档和原创测试材料；本机绑定、私人书库与作者记录留在本地。

发布版修正了检索脚本对建设期本机字典位置的依赖：字典改为工作区内的可选配置，无字典时如实报告只做大小写归一。通用脚本应能在没有原作者环境的机器上运行。

## 下一轮改进如何判断

优先观察真实使用中的问题：质疑是否准确、范例是否适用、短示范是否帮助作者继续、引用是否可追溯、跨对话能否恢复关键进度。向量检索、更复杂的作品管理或课程安排都属于候选方向，尚未因为写进文档就成为承诺或已实现功能。
